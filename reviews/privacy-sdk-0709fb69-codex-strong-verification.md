## Open findings from source inspection

1. **High — Approval metadata can still disappear during wrapping.** src/server/core/privacy-conversion.ts:25–28 spreads only own enumerable properties. A converted descriptor whose effective approval comes from its prototype or a non-enumerable property loses that requirement. An execute-only projection also loses the original SDK approval when it omits the property entirely, even though the protected reconstruction has access to the registration. For native descriptors, src/server/pii-shield/tool-boundary.ts:93–102 reads inherited approval but only writes it explicitly when it is a function. Boolean true can disappear. The installed AI SDK's is-approval-needed.ts:16–21 treats missing approval as false. An enumerable approval getter is also snapshotted by spread. Ordinary own boolean/function tests and cross-format provenance tests do not cover these cases. Preserve effective guards, their receiver and late-bound semantics, or refuse descriptors for which this is impossible.
2. **High — Single-sided loss of managed configuration can erase retained authority locally.** src/runtime/glirastes.ts:563–572 discards even an explicit fixed UUID unless a store factory or activation remains. Meanwhile a retained store with a missing binding is never consulted before discovery. After activation removal, either condition can make hasPrivacyAuthority false and release ordinary chat/speech during offline discovery at lines 824–849, 898–905. Even with the factory and binding present, FileRuntimeStateStore.load maps a missing state file to null (src/sync/state-store.ts:112–118), and the fresh-inactive/null-store case is deliberately permitted (src/runtime/__tests__/glirastes.test.ts:871–874). A fresh empty store and loss of the previous file then look identical. The documented DR exception is removal/change of *both* binding and store. Ordinary automatic pairing also emits the UUID. The implementation needs a distinguishable retained indication or a clarified, explicitly accepted operational boundary; making every paired ordinary installation require privacy storage changes ordinary compatibility. Existing offline restart coverage with both binding and intact store succeeds.
3. **High — A managed turn pinned off can dispatch an ordinary classifier after the gate locks.** src/server/adapters/nextjs/create-ai-chat-handler.ts:1845,2428–2431,2447–2489 checks at admission, then awaits approval/scope work and supplies classifier hooks only when a protected turn already exists. src/server/local-pipeline.ts:155 and src/server/core/intent-classifier.ts:376–385,413–420 can subsequently invoke the configured LLM with ordinary text/history. The final stream's prepareStep gate does not guard this separate request. A newly loaded revocation or raised protected floor during preparation can therefore be missed for that dispatch. The protected-model path itself checks both during transformation and before underlying dispatch (src/server/pii-shield/model-boundary.ts:381,460–477).
4. **High — A rejected or incomplete first active snapshot can release a cached off policy.** src/sync/sync-manager.ts:167–175 correctly verifies restored signatures, but lines 235–242,279–282,291–303,313–322 retain the prior stable deployment when active state is incomplete or rejected and still persist a current cursor. src/runtime/glirastes.ts:349 and 824–843 interpret a saved cursor and existing stable revision as successful bootstrap. A legitimately signed historical off decision can resume when the first response did not establish the current active decision. A revocation intermediate save at src/sync/sync-manager.ts:216 can likewise expose reconciliation early when restored state already carries a non-null cursor. Separate fresh authenticated reconciliation from cursor persistence and preserve last-known-good handling for already initialized runtimes.
5. **Medium — Validated envelope scope can diverge from the policy used.** src/sync/sync-manager.ts:345–362 checks expected app and, when supplied, tenant, manifest/policy environment, and prompt app. Optional explicit environment IDs on agent/config envelopes are not compared (src/contracts/revisions.ts:207–225). More importantly, src/sync/materialize-deployment.ts:22–30,32–49 spreads signed payload fields over the validated envelope identifiers, revision number and scope. Schema-valid conflicting values in an authentically signed bundle can therefore change effective floor ordering, revocation identity or scope. Verification authenticates the payload but does not require equality of its duplicate fields with the envelope. The same materializer serves restore and live use. This requires inconsistent signed material; no claim about what Platform currently emits. The normal connection lookup supplies no authenticated tenant (src/sync/connection-lookup.ts:6–21). Existing app/tenant tests exercise the envelope-only case. Revocations are environment-scoped on the wire.
6. **Medium — Direct image publication remains independently reachable.** .github/workflows/publish.yml:96–126 correctly gates its image and npm jobs on privacy preflight and native STT. But .github/workflows/runtime-container.yml:9–19,75–92 also accepts a manual publication input. Its own tagged workflow runs container tests, checks the tag and can push with package write permission without the shared privacy or native jobs. The dependency assertions in tests/release-workflows.test.ts:123–129 cover the parent workflow. Require the same gates at every publish entry point. Source inspection only.
7. **Medium — Receipt acquisition creates a policy-check gap before tool side effects.** src/server/pii-shield/tool-boundary.ts:104,132–147 checks the live policy before a potentially slow durable receipt claim. After that await the exported wrapper directly invokes the underlying execute without rechecking. A revocation loaded during receipt acquisition can be missed by a tool without an independent downstream guard. A fresh refusal immediately before execute must settle the still-unexecuted claim consistently. This concerns the public wrapper; independently guarded managed tools may have additional protection.
8. **Medium — A returned unknown outcome can become a definitive failure in conversion.** src/server/core/clean-tool-result.ts:49–53 classifies protected error-only objects as failures. src/server/core/tool-failure-result.ts:140–155 transfers the SDK unknown marker only with endpoint provenance. A composed SDK tool can return a marked non-endpoint failure, for example the result of an inner converted tool (src/server/core/index.ts:1225–1230). The outer converted result becomes a plain failure before the wrapper checks the marker at src/server/pii-shield/tool-boundary.ts:155–169. Its receipt can be completed as failed despite uncertain execution. Native marked returns, thrown recognized timeouts and endpoint-marked results follow the intended paths. Preserve the SDK marker independently of endpoint provenance.
9. **Low — Some protected diagnostics still accept caller-controlled text.** src/server/adapters/nextjs/recording-transcription-handler.ts:293–296,319–320,411 puts arbitrary Error.name from a local transcriber or transport into the emitted code and default log. In chat, src/server/pii-shield/detection-result.ts:80–85,98–99 trusts a same-module PrivacyError instance's runtime-mutable code, and uses prototype-inclusive membership for duck-typed codes. src/server/pii-shield/chat-privacy.ts:160–163,172–180 consumes those results. Fresh safe error instances fix the raw extras case, and ordinary arbitrary names are now enumerated in chat. Validate the actual code against own known codes even for nominal instances and use fixed recording diagnostics. Nest's errorName at src/server/adapters/nestjs/chat/ai-chat.service.ts:32–35 also passes arbitrary names, though its protected configuration is refused at lines 74–77.
