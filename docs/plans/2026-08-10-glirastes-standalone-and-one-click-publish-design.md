# Glirastes Standalone Mode and One-Click Publish Design

**Created:** 2026-08-10 · **Status:** Draft, awaiting operator review
**Decision basis:** Platform working document
`docs/plans/2026-07-29-glirastes-foundation-pilot-working-document.md`,
§6 entry "2026-08-04 — Beschlossenes Arbeitspaket: Standalone-Modus +
Ein-Klick-Publish".

## Outcome

The platform is an **add-on for hot-swap and governance, not a ticket of
admission**. A target app runs fully featured from locally generated
bindings, modules, and prompts without any control plane
(`glirastes scan && dev`). Connecting a control plane adds signed revisions,
approvals, hot-swap, and audit — it never becomes a prerequisite. For solo
operators the managed chain condenses into one "Publish & Deploy" step with
one audit trail; the granular chain remains for teams with four-eyes
approval.

## Non-goals

- No silent fallback from managed to unsigned execution. The rule "kein
  unsigned Fallback" stands: forbidden is the *silent* downgrade out of
  managed mode, not the *explicitly configured* standalone operation.
- No third mode. Exactly two: standalone and managed.
- No weakening of the managed safety contract (signatures, fail-closed
  principal/tenant checks, revocations, health gates).

## Mode model

| | Standalone (default) | Managed (opt-in) |
|---|---|---|
| Trigger | `GLIRASTES_CONTROL_PLANE_URL` unset | `GLIRASTES_CONTROL_PLANE_URL` + `GLIRASTES_API_KEY` set |
| Revision source | Local artifacts generated by the CLI | Signed runtime state from sync |
| Approvals / deploys | None — file change + restart | Publish → approve → deploy → activate |
| Failure behavior | Fail closed on local drift (validate gate) | Fail closed on signature/tenant/manifest drift |

Mode is resolved once at boot and logged. A managed-configured app that
cannot verify its signed state stays fail-closed — it never degrades into
standalone.

## Part 1 — Standalone runtime source

### Problem

`createAiChatHandler`'s `loadTools` requires a managed `turnSnapshot`
(`chat-handler.ts` throws without one), and prompt assembly pins managed
prompt bundles. The registry/naming stack
(`materializeManifestToolRegistry`, `modelFacingToolName`,
`assertModuleRegistryParity`) is correct and current — the missing piece is
a second *source*, not a second *pipeline*.

### Approach: one pipeline, two revision sources (chosen)

Introduce a `RuntimeSource` abstraction in `glirastes/runtime`:

- `ManagedRuntimeSource` — wraps today's sync/state-store path; yields the
  verified signed turn snapshot per turn (unchanged behavior).
- `LocalRuntimeSource` — materializes an equivalent snapshot at boot from
  the CLI-generated artifacts in `.glirastes/` (execution inventory v2,
  bindings, module membership, prompt bundles). Content is unsigned but the
  *shape* is the same `TurnSnapshot`; a `source: 'local'` discriminator is
  carried for diagnostics and guards.

Downstream of the source, **everything is shared**: registry
materialization, model-safe name encoding, module scoping with the
fail-closed drift guard, RBAC intersection, budgets, checkpoints, prompt
assembly. This is the direct lesson of the module-tool-names outage: two
worlds drift; one world with two sources cannot.

Rejected alternatives:

- *Separate standalone handler* — recreates the drift class the 04.08.
  guards were built to kill.
- *Reviving the old `local-pipeline.ts` path* — predates the definitionId
  registry and model-safe encoding; would resurrect retired naming.

### Curated semantics become first-class local artifacts

Interlocked work package (§6, 04.08. Abend, point 4): module membership,
model-facing names, and usage hints move out of app-local `module-tools.ts`
into the setup artifact, generated and validated by the CLI.

- Standalone reads them from the local artifact — this is why local
  semantics must be first-class when standalone is the default.
- Managed carries the same fields inside signed revisions; the platform
  only overrides what is explicitly configured there.
- `glirastes validate` (and therefore build/setup) gates both modes with
  the same parity checks against the generated registry.

Acceptance for the CLI side stays the operator's sentence from the pilot
machinery finding: a complete re-run is plain `glirastes setup`, no flags.

### Testing

- Contract test: both sources produce snapshots that materialize identical
  registries for identical inputs (golden fixture from the Get It Done
  pilot inventory).
- The existing parity gate `assertModuleRegistryParity()` runs in both
  modes in consumer test suites.
- Standalone boot without network access is a test case, not a manual
  claim: no fetch, no control-plane env, full turn with tool execution
  against the local source.
- Managed regression suite unchanged and green.

## Part 2 — One-click publish (managed condensed)

### Problem

The granular chain (complete review → publish → approve each revision →
deploy latest published → health gate → activate) is correct for teams but
punishing for a solo operator, and its implementation performs ~95
sequential Neon round trips on publish plus per-revision
approve/sign/audit on decisions (minutes of wall clock, observed 04.08.).

### Approach: server-side composite endpoint (chosen)

New API operation, e.g.
`POST /v2/apps/:appId/runtime-setup/runs/:runId/publish-and-deploy`
with `{ environmentId, reason }`:

1. completes the review (`ready`),
2. publishes the run's revisions **batched** (multi-row inserts inside one
   transaction — this fixes the performance finding for the granular chain
   too, since publish shares the same service),
3. records decisions as `selfApproved` with the operator identity and the
   given reason,
4. derives manifest/policy from the published configuration (key-scoped
   reuse rules unchanged),
5. creates the deployment, waits for the health gate, activates.

One audit trail entry chain records the composite action; each step's
individual audit events still exist and reference the composite id.
Partial failure leaves a consistent, resumable state (the run/deployment
states already model every intermediate), and the response names the step
reached.

Citadel gets a single **"Publish & Deploy"** button on the Runtime Setup
workspace (visible when the run is publishable and the operator's role may
self-approve); the granular controls remain for four-eyes teams.

Rejected alternative: Citadel-side orchestration of the existing endpoints
— fragments the audit trail, multiplies partial-failure UI states, and
leaves the round-trip cost unfixed.

### Testing

- Service-level TDD against the isolated Foundation DB: happy path,
  self-approval permission denied, health-gate failure (deployment stays
  pending, nothing activated), idempotent resume after step failure.
- Publish batching verified by a round-trip count assertion, not by
  timing.

## Delivery order

1. **Standalone runtime source** (SDK + Get It Done consumer proof) —
   unblocks the product default and needs no platform deploy.
2. **Curated semantics in artifacts** (SDK contract + CLI + consumer;
   managed side carries the fields in revisions on the next publish
   cycle).
3. **One-click publish** (Platform API + Citadel), including publish
   batching.

Each step lands TDD-covered on the three foundation branches; no push or
merge without operator approval, as before.

## Open questions for the operator

1. Snapshot pinning in standalone: pin per turn from the boot-time local
   source (hot reload requires restart — simplest), or re-materialize on
   file change? Draft assumes restart-only.
2. May `publish-and-deploy` also *create* the Local environment if none
   exists, or is environment creation a deliberate separate act? Draft
   assumes it must already exist.
3. Should standalone emit any telemetry at all (even content-free) or be
   strictly network-silent? Draft assumes strictly silent.
